Coverage includes production screens, routes, hooks, services, stores and adapters, including untested files. Only tests, fixtures, declarations and type directories are excluded. `artifacts/coverage/index.html` and `lcov.info` are generated by an actual Jest coverage run. Review missing branches, particularly offline failure/recovery and ownership checks, instead of adding snapshot-only assertions to raise the number.

## Commands

After installing dependencies with network access:

```sh
npm install
npm run test:core
npm run test:coverage
npm run typecheck
npm run lint
npm run test:verify
```

`test:verify` attempts every available check even if one fails, saves logs and machine-readable results under ignored `artifacts/`, and regenerates the report. It returns a nonzero exit status for failures, missing tools or unexecuted required device/database checks. This prevents a partial run being mistaken for a verified release. `test:report` reuses the latest verification metadata; old or empty coverage files are not accepted as current measurements. Syntax-only checking of `.ts` files is separately labeled and cannot replace `tsc` or check TSX types.

To include device/database checks, provision the backend/device below, set `FITHUB_RUN_E2E=1` and `FITHUB_TEST_DATABASE_URL`, then run `test:verify` again. Standalone database/E2E commands are also available.

## Mocking boundaries

Presentation tests mock service composition roots or repository interfaces, never embed Supabase calls in UI. React Hook Form, Zod, TanStack Query, application services and theme providers are real in the new Jest integration/component tests. Query retries are disabled per test and clients are cleared on unmount; app retry behavior is not changed.

Native adapters use deterministic AsyncStorage, safe-area, gesture, Reanimated, image and haptic mocks. These remove platform side effects without claiming native permission/animation correctness. Auth mocks return explicit session/confirmation states. Repository tests verify owner scope, cancellation, pagination and RPC parameters. Offline core tests additionally use Node's real SQLite engine to verify durable behavior. Maestro uses real networking/auth/database/storage rather than mocks.

Avoid testing private hooks or internal component state. Assert accessible user actions, validation messages, submitted domain values, server-port effects, preserved local data and deterministic public results. Existing reorder tests use the accessible move buttons; Maestro/native manual checks remain necessary for actual long-press drag gestures, animations, permissions and screen-reader behavior.

## Database security/workflow execution

Apply every migration and seed to a disposable **local** Supabase instance first. Use PostgreSQL client tools and a postgres test connection supplied privately through `FITHUB_TEST_DATABASE_URL`; never put service credentials in `EXPO_PUBLIC_*` or source control.

```sh
npm run test:database
```

The runner discovers all ten `supabase/tests/*.sql` suites, stops each script on SQL errors, and restricts its connection to loopback. Every suite wraps fixtures in a transaction ending in `rollback`; an aborted connection also rolls back. Application operations in the new journey run as `authenticated` with actor claims, while Auth fixtures are created by postgres. This tests profile automation, not Supabase Auth's HTTP registration endpoint; Maestro covers that endpoint. `db:verify` performs static migration checks only.

## Maestro prerequisites and execution

Install Maestro and a running Android emulator/device or iOS simulator with the FitHub development build (`com.fithub.app`). Expo Go is not this application ID. Apply migrations/seed to a dedicated local backend reachable from the device; configure the build's public Supabase URL/key normally. Android emulator host access commonly requires an emulator-reachable host address rather than device loopback. Never point these flows at real users' data.

For **local E2E only**, configure Supabase email confirmations off so the registration flow can reach Home without mailbox automation. Do not disable production confirmation or add an auth bypass. Start with fresh app data; flows clear app-local data, not remote records. They do not delete production or existing database content.

Set these private shell variables before running:

- `E2E_RUN_ID`: fresh 1–16 character lowercase/digit/underscore suffix, e.g. `run20261008a`.
- `E2E_PASSWORD`: test-only password with at least eight characters.
- `E2E_SUPABASE_URL`: local host Supabase endpoint, normally `http://127.0.0.1:54321`, for the provisioning script.
- `E2E_SUPABASE_SERVICE_ROLE_KEY`: local-only admin credential; never bundle it or commit it.

```sh
npm run test:e2e:provision
```

This creates one confirmed local actor with username `e2e_<runId>`, email `e2e_<runId>@example.test`, display name `E2E Athlete`, metric units and beginner experience. It refuses non-loopback endpoints. Set `E2E_EMAIL` to the emitted test email, then:

```sh
npm run test:e2e
```

Maestro resolves the `E2E_*` environment values. Output includes JUnit at `artifacts/maestro-results.xml` and workspace artifacts under `artifacts/maestro`. Use a new run ID when re-running: account creation is deliberately not silently reused, so unique constraints remain tested.

| Flow | Scenario |
| --- | --- |
| `01-authentication.yaml` | Register a second fresh account, reach named Home greeting, log out and log in with the same credentials |
| `02-workout.yaml` | Create workout, add seeded Back Squat, configure one 8-rep set at 20 kg, save/start/complete, assert 1 set / 8 reps / 160 kg·reps summary, save and verify synchronization |
| `03-challenge.yaml` | Create public count challenge with inclusive current UTC dates, verify creator enrollment, leave/rejoin, verify rank and leaderboard |
| `04-measurement.yaml` | Add 80 kg / 85 cm measurement, verify canonical history and dashboard latest weight |

The challenge scenario explicitly re-joins because creators are automatically enrolled; it does not pretend creation exposes a first-join button. Multi-user invitation/authorization and duplicate scoring are additionally covered by client and SQL tests. Flows use visible text/accessibility descriptions, conditional achievement dismissal and bounded waits/scrolling, not pixel coordinates or fixed sleeps. They are authored, not device-validated here; inspect selectors on both platforms when the native build is available.

Maestro's [workspace configuration](https://docs.maestro.dev/reference/workspace-configuration) selects only `flows/*.yaml`, keeping shared login out of automatic discovery. [JUnit output](https://docs.maestro.dev/maestro-flows/workspace-management/test-reports-and-artifacts) is configured through the CLI. The obsolete placeholder smoke flow was removed.
